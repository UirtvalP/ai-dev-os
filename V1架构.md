# AI Workspace Orchestrator V1 Architecture

## 1. 项目定位

本项目是一个面向 AI Coding Agent 的持久工作区编排系统。

它不替代 Codex、Claude Code、Cursor、dashi-taskboard 或 Git，而是在这些工具之上增加一层统一的 Workspace / Requirement / Workflow 管理。

核心目标：

1. 一个需求拥有独立、持久的 Workspace。
2. 一个需求可以跨越多个 Agent Session / Thread。
3. Thread 只是临时执行上下文，不是需求的 Source of Truth。
4. Agent 每次进入一个需求时，都可以自动恢复必要上下文。
5. 根据任务复杂度自动选择轻量或完整工作流。
6. 任务状态可以同步到 dashi-taskboard。
7. Git branch / worktree 与任务关联。
8. 为未来接入 Multica、多 Agent、Obsidian 留出 Adapter 接口。
9. V1 优先保证简单、快速、可靠，不实现复杂自治 Agent 系统。

---

# 2. 核心设计原则

## 2.1 Workspace First

不要把 Conversation / Thread 当成项目上下文。

正确模型：

```text
Requirement Workspace
        ↓
Persistent State
        ↓
Task Graph
        ↓
Session / Thread
```

而不是：

```text
Thread
  ↓
所有需求上下文
```

Thread 可以随时结束、替换。

Workspace 必须长期存在。

---

## 2.2 Sessions Are Disposable

每一个 Codex Thread 都只是一个 Session。

一个 Requirement 可以关联任意数量 Session：

```text
REQ-001
├── Session A
├── Session B
├── Session C
└── Session D
```

新 Session 不依赖旧 Session 完整聊天历史。

它只通过 Workspace Snapshot 恢复上下文。

---

## 2.3 Source of Truth 必须明确

不同信息分别由不同系统负责。

### Workspace

负责：

- Requirement
- Acceptance Criteria
- 当前阶段
- Plan
- Architecture Decisions
- Handoff
- Verification
- Context Snapshot

### dashi-taskboard

负责：

- Task
- Status
- Priority
- Parent / child
- blocks / blocked_by
- Session / Thread ID
- Git branch
- Git worktree

### Git

负责：

- Code State
- Commit
- Branch
- Diff

### Agent

负责：

- 当前执行

Agent Conversation 不属于 Source of Truth。

# 5. Workspace 文件结构

每一个 Requirement 创建独立目录。

例如：

```text
.workspace/
└── REQ-001/
    ├── meta.json
    ├── requirement.md
    ├── state.md
    ├── plan.md
    ├── decisions.md
    ├── verification.md
    ├── handoff.md
    └── sessions.json
```

---

# 6. meta.json

保存机器可读元数据。

例如：

```json
{
  "id": "REQ-001",
  "title": "Implement authentication system",
  "status": "in_progress",
  "complexity": "normal",
  "workflow": "normal",
  "created_at": "2026-08-29T00:00:00",
  "updated_at": "2026-08-29T00:00:00",
  "task_provider": "dashi",
  "agent_provider": "codex",
  "git": {
    "branch": "feature/REQ-001-auth",
    "worktree": ".worktrees/REQ-001"
  }
}
```

meta.json 不保存长文本上下文。

长文本放 Markdown。

---

# 7. requirement.md

这是 Requirement 的稳定定义。

格式：

```markdown
# Requirement

## Goal

实现用户登录认证。

## Background

当前系统没有统一认证机制。

## Scope

- 登录
- Token 生成
- Token 校验

## Non-goals

- OAuth
- 第三方登录

## Acceptance Criteria

- [ ] 正确账号密码可以登录
- [ ] 错误密码返回 401
- [ ] Token 可以访问受保护 API
- [ ] 过期 Token 无法访问
```

规则：

Requirement 一旦进入执行阶段，不允许 Agent 随意改变 Goal / Scope。

如果用户需求发生变化，应记录 change，而不是静默改写历史需求。

---

# 8. state.md

保存当前实时状态。

格式：

```markdown
# State

## Phase

implementation

## Completed

- User model
- Password hashing

## In Progress

- Login endpoint

## Pending

- Auth middleware
- Integration tests

## Blocked

None

## Next Action

Implement login endpoint validation.
```

这是 Restore 时最重要的文件之一。

---

# 9. plan.md

保存当前任务计划。

格式：

```markdown
# Plan

- [x] Inspect existing user model
- [x] Add password validation
- [-] Implement login endpoint
- [ ] Add authentication middleware
- [ ] Add tests
```

规则：

Tiny Task 可以不创建详细 plan。

Normal Task 使用简短 plan。

Complex Task 才允许使用详细 Task Graph。

---

# 10. decisions.md

记录重要决策。

格式：

```markdown
# Decisions

## DEC-001

Date: 2026-08-29

Decision:

Use JWT for authentication.

Reason:

- Existing stateless backend
- No server-side session infrastructure

Rejected:

- Server sessions
- OAuth
```

只记录真正影响未来工作的决策。

不要记录：

```text
修改 foo.py 第 23 行
```

---

# 11. verification.md

保存验证状态。

```markdown
# Verification

## Unit Tests

Command:

pytest tests/auth

Status:

PASS

## Type Check

Status:

PASS

## Integration Tests

Status:

TODO
```

Requirement 是否可以进入 review，必须参考 Verification。

---

# 12. handoff.md

这是 V1 最核心文件之一。

每次 Session 结束时更新。

例如：

```markdown
# Handoff

## Last Session

Session ID:

codex-thread-xxx

## Completed

- Implemented login endpoint
- Added password validation

## Files Changed

- src/auth/login.py
- tests/test_login.py

## Current State

Login endpoint works.

Authentication middleware has not been implemented.

## Important Context

Do not move token validation into UserService.

Authentication logic should remain in auth module.

## Next Recommended Action

Implement authentication middleware.

## Known Problems

None.
```

新的 Thread 启动后，应该优先读取 handoff，而不是依赖历史 Conversation。

---

# 13. Session 模型

sessions.json：

```json
[
  {
    "id": "thread-001",
    "agent": "codex",
    "started_at": "...",
    "ended_at": "...",
    "task_ids": [
      "TASK-001"
    ],
    "result": "completed"
  }
]
```

Session 只负责记录：

- 哪个 Agent
- 哪个 Thread
- 执行过哪些 Task
- 什么时候开始/结束
- 最终结果

不要把完整聊天记录存进去。

# 14. Complexity Router

这是为了避免 Superpowers 式过度思考。

支持：

```text
tiny
normal
complex
research
```

默认：

```text
normal
```

但明显简单任务应自动降级为 tiny。

---

# 15. Tiny Workflow

适合：

- 小 Bug
- 简单 UI 修改
- 文案
- 明确的空指针
- 明确的条件判断错误
- 小范围配置修改

流程：

```text
inspect
↓
fix
↓
verify
↓
checkpoint
```

禁止：

- 长篇 brainstorming
- architecture design
- 创建复杂 task graph
- 大范围代码扫描
- 无必要的 alternative analysis

Agent 指令：

```text
Prefer execution over planning.

Only inspect code directly related to the issue.

Do not create a multi-stage design unless the issue proves broader than expected.
```

如果发现影响范围扩大：

```text
tiny → normal
```

---

# 16. Normal Workflow

适合绝大多数日常开发任务。

流程：

```text
restore
↓
understand
↓
plan-lite
↓
implement
↓
verify
↓
checkpoint
↓
handoff / review
```

Plan 最多保持简短。

例如：

```text
1. inspect auth module
2. implement middleware
3. add tests
```

不需要写几百行设计文档。

---

# 17. Complex Workflow

只有满足以下条件之一才进入：

- 跨多个模块
- 数据库 schema 变化
- API contract 大改
- 新系统
- 架构调整
- 高风险功能
- 多个 Task 存在依赖关系
- 用户明确要求设计

流程：

```text
restore
↓
requirement analysis
↓
design
↓
task graph
↓
implementation
↓
integration
↓
verification
↓
review
```

Complex Workflow 可以允许更深分析。

但仍然必须避免无意义反复推演。

---

# 18. Research Workflow

适合：

- 技术选型
- Debug root cause 未知
- 性能调查
- 架构调研

流程：

```text
question
↓
investigate
↓
evidence
↓
compare
↓
decision
↓
knowledge candidate
```

---

# 19. Complexity 自动升级规则

允许升级：

```text
tiny → normal → complex
```

不建议自动降级正在执行的 Workflow。

Tiny 升 Normal 示例：

- 修改范围超过预期
- 涉及多个模块
- 原因不是局部 bug
- 需要修改测试架构

Normal 升 Complex：

- schema migration
- public API break
- 重大 architecture decision
- 需要并行多个子任务
- 出现明显 cross-module dependency

升级时记录：

```text
Workflow upgraded from normal to complex.

Reason:
Authentication change affects API contract and database schema.
```

# 20. Restore Protocol

每次：

```bash
workspace resume REQ-001
```

执行：

```text
1. Load meta.json

2. Load requirement.md

3. Load state.md

4. Load handoff.md

5. Load plan.md

6. Load decisions.md

7. Load verification.md

8. Query dashi Task State

9. Inspect Git branch/worktree

10. git status

11. inspect recent commits

12. build Context Snapshot

13. determine Next Action

14. start/resume Agent Session
```

---

# 21. Context Snapshot

Restore 后给 Agent 的上下文不要是所有文件原样拼接。

应生成精简 Snapshot：

```markdown
# Workspace Context

Requirement:
REQ-001 Authentication

Goal:
Implement JWT authentication.

Current Phase:
Implementation

Current Task:
TASK-003 Authentication Middleware

Completed:
- User model
- Login endpoint

Pending:
- Middleware
- Integration tests

Important Decisions:
- JWT
- Auth logic stays in auth module

Git:
branch: feature/REQ-001-auth
worktree: .worktrees/REQ-001

Verification:
Unit tests PASS
Integration tests TODO

Last Handoff:
Login endpoint completed.

Next Action:
Implement auth middleware.
```

目标：

**让新 Thread 用最少 Token 恢复最关键上下文。**

---

# 22. Checkpoint

Checkpoint 不等于 Handoff。

Checkpoint 是当前 Thread 还可能继续，但需要持久化状态。

命令：

```bash
workspace checkpoint REQ-001
```

执行：

```text
update state.md
update plan.md
update verification.md
update dashi task
record current session
```

适合：

- 完成一个小阶段
- 即将开始新的 Task
- 长任务处理中

---

# 23. Handoff

Handoff 表示：

```text
当前 Thread 可以结束
```

执行：

```text
checkpoint
+
generate handoff.md
+
record session
+
recommend next action
```

之后用户可以直接新开 Thread：

```bash
workspace resume REQ-001
```

# 27. Codex Adapter

V1 只做 Codex。

不要一开始支持所有 Agent。

抽象：

```python
class AgentProvider:
    def build_context(...)
    def get_current_session_id(...)
    def record_session(...)
```

V1 的 Codex Adapter 可以先只负责：

- 获取 CODEX_THREAD_ID
- 构造 Workspace Context
- Session 记录

不要求 V1 自动启动 Codex。

因为 Skill 本身就在 Codex 里执行。

# 28. Skill 设计

Skill 应该非常薄。

不要再复制 Superpowers 那种大量固定工作流规则。

Skill 主要负责：

```text
1. Detect workspace

2. Call restore

3. Read generated Context Snapshot

4. Follow selected workflow

5. Execute task

6. Update checkpoint

7. Generate handoff when needed
```

核心原则：

```text
The workspace system owns state.
The skill follows the workspace.
```

而不是：

```text
Skill owns all state.
```

---

# 29. Skill 的核心 Prompt 原则

必须明确写：

```text
Default to the lightest workflow that can safely solve the task.

Do not perform architecture analysis for tiny fixes.

Do not create plans merely for process compliance.

Prefer direct execution when:
- the root cause is obvious,
- the blast radius is small,
- the expected change is local.

Escalate workflow only when evidence justifies it.
```

这条非常重要。



# 35. V1 Acceptance Criteria

## Requirement Workspace

- [ ] 可以创建 Requirement
- [ ] Requirement 有稳定 ID
- [ ] Workspace 文件自动初始化

## Task

- [ ] 可以通过 dashi 创建 Task
- [ ] Task 与 Requirement 建立关联
- [ ] 可以更新状态

## Session

- [ ] 能记录 CODEX_THREAD_ID
- [ ] 一个 Requirement 支持多个 Session
- [ ] Session 切换不会丢失 Requirement 状态

## Restore

- [ ] 新 Thread 可以恢复 Requirement
- [ ] 可以读取 handoff
- [ ] 可以读取 Git 状态
- [ ] 可以读取 Task 状态
- [ ] 自动生成 Context Snapshot

## Workflow

- [ ] 支持 tiny
- [ ] 支持 normal
- [ ] 支持 complex
- [ ] 支持 research
- [ ] tiny 默认不进行长规划
- [ ] 可以根据证据升级 workflow

## Checkpoint

- [ ] 更新 state
- [ ] 更新 plan
- [ ] 更新 verification

## Handoff

- [ ] 自动生成 handoff.md
- [ ] 记录完成内容
- [ ] 记录下一步
- [ ] 记录重要上下文

## Review

- [ ] 检查 Acceptance Criteria
- [ ] 检查 Verification
- [ ] Agent 不能直接标记 Requirement done

# 37. 核心工程原则

## Principle 1

Do not store knowledge only in conversation history.

## Principle 2

Do not force full planning on simple work.

## Principle 3

Prefer execution over ceremony.

## Principle 4

Persistent state must be human-readable.

因此优先：

```text
Markdown + JSON
```

而不是数据库。

## Principle 5

Adapters must isolate external tools.

Core 不允许直接依赖：

```text
taskctl
codex
obsidian
multica
```

必须通过 Adapter。

## Principle 6

V1 must remain local-first.

## Principle 7

Every session must be replaceable.

如果一个 Thread 无法被替换，则说明持久状态设计失败。

# 40. 给 Codex 的开发要求

实现时必须遵守：

1. 不要超出 V1 Scope。
2. 不要提前实现 Web UI。
3. 不要添加数据库。
4. 不要实现复杂 Agent Framework。
5. 不要复制 Superpowers 的重型流程。
6. 优先完成 Restore / Checkpoint / Handoff。
7. 所有外部工具必须通过 Adapter。
8. Core 必须可以在没有 dashi 的情况下运行。
9. dashi Adapter 是可选集成。
10. 所有 Workspace 文件必须人类可读。
11. 必须为核心生命周期写测试。
12. 对 tiny task 优先直接执行，不允许无意义长规划。
13. 每完成一个 Phase 后先验证，再进入下一 Phase。
14. 如果发现需求与本架构冲突，不要自行扩大 Scope，记录问题并继续保持 V1 最小实现。
